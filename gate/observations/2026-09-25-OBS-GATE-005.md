## The web app's grace period

The maintainer asked that a signed-in user stay signed in through an outage,
and be signed out if it lasts three minutes or more. That is the web app's
side of the fix (`lib/sessionGrace.ts`, `hooks/useAuth.ts`, the query client in
`providers/trpc.tsx`); the gate's driver is not the web app, so no world judges
it, and its tests do. The user is signed out only on evidence: a session check
that still fails three minutes after the first failed one, timed on the
monotonic clock so a change to the system clock cannot shorten it. Checks run
every 15 s while failing, in a hidden tab too, and once a minute while healthy;
every session call gives up after 10 s. The app then keeps the user signed out,
in every tab and across reloads, until the server has ended the session or they
sign in again, and a server sign-out never overlaps a sign-in.

Three adversarial review rounds shaped it. The first two found and confirmed
defects in the first two designs, all fixed: a page loaded during an outage
went to the login page after 3 s; signing in again after an outage sign-out was
undone; an ordinary sign-out and sign-in bounced once; a failing server
sign-out was re-sent on every render; a hidden tab could sign every tab out
after a short outage, or never gather evidence at all; an open page did not
notice an outage; tabs could undo each other's sign-in; a re-check cancelled
the check under way; and session calls had no timeout. The third round's
reviewers finished, but the run stopped with 9 of their findings verified. Of
those, fixed: a sign-in that failed during an outage cleared the pending
sign-out and revived the old session. Confirmed and still open: sign-in and
sign-out calls made while the browser is offline pause rather than fail,
outlast the session lock and can later end a newer session; where the
monotonic clock runs through sleep, one failed check before sleep and one after
count as three minutes; and a sibling subdomain can set the flag cookie. The
round's unverified findings remain to be checked.

The invariants and bounds are listed in `lib/sessionGrace.ts`. Each is pinned by
a unit test and by a system test that runs the real query client, tRPC client,
guard and login page against a fake server (`__tests__/useAuthOutage.test.tsx`).
Of 26 deliberate breakages of the code, 25 made a test fail; the other only
removes a redundant check.

## Corrections

OBS-GATE-004 said that during the outage the auth guard sends a user to the
login page. That holds only for a page loaded or reloaded during the outage: an
open page keeps its signed-in user, since a failed re-check keeps the last
answer. OBS-GATE-004 carries the correction.

## Findings

1. **Fixed: a database outage signed people out** (OBS-GATE-004, finding 1),
   in `a47caf6`, with the web app's grace period on top.
2. **The database world under `actions` rarely tests sessions.** Addressed by
   the `sessions` world; the `actions` world stays for what it was for:
   durability and delivery across a database restart.
3. **Still open: the audit writer's deadlock** (OBS-GATE-001, finding 2).
4. **Not exercised: persona sessions during a database outage.** Since
   2026-09-26 the server answers a persona session from its token while the
   database is down, unless persona login is off in production. The gate's
   driver signs in with credentials, so no world here reaches that path.
