# OBS-GATE-008: `api.read_your_writes` fails on a stack that serves stale reads

2026-09-28 (UTC). Tool: `thesis` v0.1.0-phase0, on the build host, which has
Docker again. Lock `sha256:dbf08316…`: `thesis oracles verify` reported
`oracle lock OK`, with the warning that the oracle programs differ from those
the lock recorded, because they were rebuilt here (OBS-GATE-007, 3).

Pre-registration 9 left one check for when the build host had Docker. The
oracle had to be shown able to fail on a stack, not only on synthetic
histories:

> the `api` world on images built from a scratch worktree of this commit in
> which `GET /api/v1/objects` answers from a copy of each object kept for
> 30 s, reverted afterwards. Prediction: **FAIL, exit 1**,
> `api.read_your_writes` violated with `stale_read`, since a client reads a
> person it or another client read less than 30 s before.

OBS-GATE-006 recorded this check as pending (its finding 2).

## What ran

- A scratch worktree at `820937d`, the commit of pre-registration 9, whose
  lock is the one `master` still holds. It carried one change, which was never
  committed: [`canfail.diff`](2026-09-28-OBS-GATE-008/canfail.diff).
  - `GET /api/v1/objects` answered from a copy of each object it had found in

  - An object not found was not kept.
- The images were built by that worktree's `scripts/build-images.ps1`:
  `ontos-app:canfail-820937d` and `ontos-gate-db:canfail-820937d`. The built
  `dist/boot.js` was checked to hold the copy.
- The driver and oracle checkers were built by that worktree's
  `scripts/build-tools.ps1`.
- The command, on the build host (Windows):
  `$env:ONTOS_GATE_TAG = "canfail-820937d"; thesis run --profile api`.

## Against pre-registration 9

| Run | Verdict | Prediction |
|---|---|---|
| `r_2026_09_28_10f9` | **FAIL, exit 1**: `api.read_your_writes` violated, `stale_read 2` | FAIL, exit 1, `stale_read` |

The prediction held. The oracle's account:

> a client did not read back what the Ontology API had acknowledged
> (stale_read 2). First, at t+2787ms: submission 40 on
> person/hr:Person/E-0157 was acknowledged, and the next read found an object
> naming the earlier submission 11 as its last change. 21 submission(s) through
> the API, 21 acknowledged; 21 judged by the client's next read (19 saw their
> own write, 0 a later one, 0 of those by a write the history does not name),
> 0 not judged.

Both stale reads are the kind the pre-registration expected: a client reads a
person that another client had read within the last 30 s. The notes show it.
In the first, the acknowledged note is client 2's (`…/2/6`), and the note read
back is client 5's (`…/5/1`), from submission 11. The read returned the copy
kept when client 5 read that person earlier. The second is the same, on
`E-0197`: client 3's submission 43 read back as client 5's submission 36.

The other oracles:
- `no_crash`, `no_panic_log`, `availability_after_heal`, `no_stuck_op`,
  `actions.delivered` (27 side effects), `actions.durable` (29 submissions),
  `jobs.lease_lapse` and `session.honoured`: all ok.
- `sync_jobs.settle`: **inconclusive**. The history holds no sync operation:
  48 operations, `action` 6, `api_action` 21 and `api_read` 21. This is the
  vacuous API world of OBS-GATE-007, part 1. A violation decides the verdict
  either way.

The evidence is in [`2026-09-28-OBS-GATE-008/evidence`](2026-09-28-OBS-GATE-008/evidence/r_2026_09_28_10f9):
`verdict.json`, the world file, `result.json` with every oracle's account, and
the driver's history and log. `bundlescan` scanned the run's 27 files and found
nothing to redact or refuse; its manifest is `REDACTIONS.txt`. The driver log
gives each API token's first characters only.
