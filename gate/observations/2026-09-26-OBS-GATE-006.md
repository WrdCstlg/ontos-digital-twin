CI keeps no run bundle, so the oracle's explanation, with the number of reads it
judged, is not on record. The runs count all the same, by what a PASS requires:
`api.read_your_writes` answers inconclusive when none of a world's API
submissions was judged, and one inconclusive oracle makes the run INCONCLUSIVE,
not PASS; and a driver that refused at start makes a world without imports,
which `sync_jobs.settle` cannot pass. So in each of these runs the driver ran,
made API submissions (12 in 17 of its operations), and at least one read was
judged, none stale.

The database worlds count for reads after the outage. Whether the driver
recorded an API request answered during it, the second condition, cannot be
shown without the history: not counted for the outage.

Pending, on the build host once it has Docker: runs that keep their bundles,
and the pre-registered check that the oracle can fail on a stack (the `api`

## Findings

1. **The Ontology API reads back what it acknowledged**, alone, with the app
   restarted and with the database restarted, on both remotes.
2. **Not yet shown on a stack: that `api.read_your_writes` can fail.** Its tests
   show it over synthetic histories; the stack check waits for Docker.
3. **CI cannot show what a run judged.** The maintainer has deferred keeping run
   bundles in CI (OBS-GATE-005 records the same limit for pre-registration 8).
