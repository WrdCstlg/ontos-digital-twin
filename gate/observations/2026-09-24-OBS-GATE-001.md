8 CPUs. Tool: `thesis` v0.1.0-phase0, installed with `go install` (so its
verdicts say `unstamped`). Oracle lock `sha256:e1b362c3…`, taken in commit

([`.prothesis/PREREGISTRATION.md`](../.prothesis/PREREGISTRATION.md)) before

## Against the pre-registration

Held, on today's code (`r_2026_09_24_c75a`):

- FAIL, exit 1, one violation, `sync_jobs.settle`. `no_crash`, `no_panic_log`,
  `no_stuck_op` and `availability_after_heal` all ok.
- The witness: jobs 7, 8 and 9 still `running`, with `started_ms` 3130, 3130
  and 4130, inside the predicted 1000 to 5000.
- The mechanism, in the app's own log: SIGTERM at 04:55:53.506 UTC, and 100 ms later
  the catch block's `update sync_jobs set status = …` failed with
  `Pool is closed.`, twice.

Held, after the fix (`r_2026_09_24_cbab`): PASS. The same mechanism stranded
jobs (`Pool is closed.` twice at SIGTERM), and the restarted app logged
`[boot] marked 3 abandoned sync job(s) as failed` before serving. The pass is
the fix working, not an import missing the fault.

Held, with the fix reverted (`r_2026_09_24_ad1f`): FAIL again (job 70), and the
restarted app logged no reconciliation.

Not predicted:

- **Job 9 began after SIGTERM.** `closeDb` resets the pool singleton, so a
  request arriving during shutdown builds a fresh pool with `getDb()`, writes a
  new `running` job, and dies with the process. The window between SIGTERM and
  the HTTP server closing accepts new work that cannot finish.
- **Slow recovery, once.** In `r_2026_09_24_c75a` the app logged `Server
  running` 12.7 s after SIGTERM, requests to its published port ended `EOF` for
  about 9 s after that, two hung until the driver's 8 s timeout, and HEAL took
  22.4 s. In the two later `stuckjob` worlds the app was back within about 3 s
  and HEAL was normal. The likeliest cause is Docker Desktop's port forwarding on
  the build host rather than Ontos, but this was not established.

## Findings

1. **Stranded sync jobs** (the pre-registered bug). Fixed in `a27b351`. The
   graceful shutdown still closes the pool before the server, so in-flight
   requests fail rather than finish; the fix makes the job list truthful
   afterwards, and a better shutdown order is a separate change.
2. **Concurrent imports deadlock in the audit writer. Not yet fixed.** In
   `r_2026_09_24_e7ff`, worlds 2 and 3, with no fault, one import each returned
   HTTP 500. The app log shows `writeAudit`'s insert failing with `Deadlock found
   when trying to get lock; try restarting transaction`. By then `runSync` had
   already committed the import and marked the job `succeeded`; its catch block
   then overwrote that with `failed`. So the data is imported, the job says it
   failed, and the hash-linked audit log has no entry for it. No oracle covers
   audit completeness yet, which is why the smoke run passed.

## For the PRO-THESIS side

- `proc.restart` was realized in three recorded worlds here, the first anywhere,
  and behaved as documented: `docker stop`, `docker start`, rebinding by label.
- HEAL took 22.4 s in `r_2026_09_24_c75a` against 0.1 s in the no-fault worlds
  and about 3 s in the other two `stuckjob` worlds. The world file and verdict
  are in the evidence.
- `thesis oracles list` lists `.prothesis/oracles/README.md` as an external
  oracle with no phases. It is only a digest entry; only `*.yaml` definitions
  run.
- The lock fingerprints `bin/oracle-sync-jobs.exe`, so a Linux checkout will
  report the executable as moved (a warning, not exit 4).
- Violation witnesses carry absolute paths (`oracle_definition`, `stderr_path`),
  which is the pending run-relative-paths item.
